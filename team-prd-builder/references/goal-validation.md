# 目標導向的機器驗證

## 驗證哪些事

1. 結構檢查：ID、引用、五層定位、核准證據及圖源可呈現。
2. 規格參考模型：以明確的規則與獨立預期檢查數值邊界、狀態轉移及拒絕。這不是產品實作。
3. 真實系統測試：有實作、已確認介面及授權環境時，建立對應測試。沒有時記未執行。
4. 人工核准：PM、工程與QA確認業務、可行性與驗收。機器不能驗證核准證據真實性。

任何一項通過都不能自動推導其他項通過。不可把產生器單元測試當PRD業務測試，也不可把參考模型當已實作系統。

## 追溯與測試預期

每個目標有穩定ID。目標連FR；驗證契約連目標、FR與BR；測試連契約、目標、FR及AC。以不同檔案保存契約與案例，案例的expected由來源或PM確認，不從執行結果回填。

規則、目標、契約或案例尚未確認時，正式執行記blocked_pending_pm。不要選默認值、猜測數值或把unknown當成功。測試不能覆蓋的目標列gap及Q，不能以只通過一個案例宣稱全部目標通過。

已核准契約與案例用D.approved_fingerprints鎖定內容。更改規則、輸入、預期或追溯會使舊核准失效。先取得PM確認，再記新指紋；計算指紋不代表AI可以核准。

內建number_range契約只接受有限JSON數字，明確列欄位、最小與最大值。transition契約列狀態、事件及允許轉移。沒有列出的轉移拒絕；拒絕時狀態不變。這兩種語意需PM確認後才能成為正式規格。其他公式、守恆或不變性由工程建立專用測試，不猜測通用契約。

合成範例可用--example執行，僅在所有引用來源均為example且無人類核准聲稱時開放。結果標example_only，不改規格為confirmed，也不計入正式通過。

## 交付與展示

交付validation/contracts.json、cases.json、run_spec_tests.py、results.json。執行器只讀JSON，不執行JSON中的程式、指令或HTML，不連外或操作真實系統。

```sh
python validation/run_spec_tests.py --output validation/results.json
```

只有教學合成資料才能另加--example。正式模式對未核准案例保留阻擋，不靜默跳過後宣稱全部通過。結果保留案例ID、目標、FR、AC、expected、actual、狀態及輸入檔SHA-256。

DOCX最後展示：目標覆蓋、正常及反向案例、執行命令、各類測試結果、未驗證範圍。變更契約或案例後需重跑；已有結果必須與新輸入雜湊一致。案例失敗、無案例、全部阻擋或範例通過，都不能報正式規格通過。
